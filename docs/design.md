# 설계 원리: 실제 운영판에서 수업용 키트까지

## 현재 운영 중인 메일 승인함의 구조

이룸의 Discord 메일 채널은 일반 OpenClaw Discord 채팅만으로 구현된 것이 아닙니다. **Himalaya(IMAP/SMTP) + Node.js 상태 머신 + OpenClaw 모델 실행 + Discord REST API + macOS LaunchAgent**가 결합된 별도 자동화입니다. 현재 운영 소스는 `team-hanirum/scripts/email-workflow.js`와 `scripts/lib/email-workflow-*.js`에 있습니다. 개인 설정·원장·토큰은 공개하지 않았습니다.

1. 두 메일 계정의 INBOX를 **15분마다** 읽습니다. 시작할 때 현재 메시지 ID를 기준선으로 저장하므로 기존 메일을 갑자기 처리하지 않습니다.
2. 규칙으로 보안·계정·결제·계약·거래 메일을 보호하고, 명백한 홍보/뉴스레터 및 자동 알림은 별도 처리합니다. AI는 본문을 신뢰할 수 없는 입력으로 취급하며 한국어 **구체적 요약·직접 요청 여부·추천 행동**을 추출합니다. 모든 메일을 Discord로 전송하지 않습니다.
3. 판단이 필요한 메일은 소유자를 멘션한 **채널 카드 1개 + 메일별 스레드 1개**로 올립니다. 카드에는 발신·제목·요약·추천, 스레드에는 답장 초안과 행동 카드가 있습니다.
4. 별도 작업이 **1분마다** 승인 스레드를 확인합니다. 소유자 ID만 인정하고, 결정 카드의 반응이 둘 이상이면 아무 행동도 하지 않습니다. 실제 운영판은 ✅ 발송, 🔁 이번 발송+조건 일치 시 미래 자동응답, 🗑️ 휴지통, 🙅 답장 불필요, 🚫 스팸/발신자 차단, ⏸️ 보류, 🤝 스레드 한정 협상 자동과 명시적 텍스트 수정/답장을 지원합니다. 공개 키트에는 🤝를 뺀 여섯 가지와 글 수정이 들어 있습니다.
5. 발송 전 보낸편지함에서 **같은 수신자·제목·시각**의 답장을 확인합니다. `sending` 상태를 원장에 먼저 기록한 뒤 SMTP를 호출합니다. 응답이 불확실하면 자동 재발송하지 않고 실제 Sent를 먼저 확인합니다. 발송 확인·처리 완료 뒤 스레드/카드를 정리합니다.
6. 이룸에게만 허용된 예외가 있습니다. 표준 브랜디드 영상 견적 등 **사전에 승인된 정확한 문안**은 자동 회신하고, 명시적 🔁로 만든 유사메일 규칙은 계정·발신자·제목·계약/금액/일정의 동일성 검증을 통과해야 작동합니다. 견적 자동 회신은 **이룸 개인 정책**이라 공개 키트에 없습니다.

## 왜 이렇게 나눴나

- **메일 수집과 판단 분리:** IMAP은 원본을 보존하고, AI는 요약·추천·초안만 만듭니다. 모델 판단만으로 발송하거나 파기하지 않습니다.
- **주의력 절약:** 뉴스레터/알림을 그대로 중계하지 않고 행동이 필요한 것만 채널로 올립니다. 요약은 원문 인용이 아닌 핵심과 추천 행동입니다.
- **사람 중심 승인:** Discord는 메일 저장소가 아니라 승인 UI입니다. 소유자 확인, 한 장의 최신 결정 카드, 반응 충돌 거부로 오동작을 줄입니다.
- **상태 원장과 멱등성:** 계정+메일 ID로 중복 수집을 막고, 외부 부작용 전에 상태를 기록합니다. 타임아웃은 실패의 증거가 아니므로 재전송·재삭제하지 않습니다.
- **검증 가능한 완료:** SMTP 접수와 실제 Sent 확인을 구분합니다. 알림 전송, 이메일 발송, 메일 이동도 각각 결과를 확인합니다.
- **신뢰 경계:** 이메일 본문은 프롬프트 인젝션 가능성이 있는 외부 데이터입니다. 메일에 적힌 명령·링크가 에이전트의 권한을 바꾸지 못해야 합니다.
- **계정·권한 최소화:** 수강생은 자기 IMAP/SMTP 계정, 자기 Discord 봇, 비공개 승인 채널을 사용합니다. 원장과 토큰은 로컬 비공개 파일에 남깁니다.

## 공개 스타터의 의도적 차이

| 항목 | 이룸 운영판 | 이 저장소의 수업용 스타터 |
| --- | --- | --- |
| 수집/승인 주기 | 메일 15분 / 승인 1분 | 메일 5분 / 승인 1분 |
| AI 권한 | 현재 운영 에이전트 설정에 의존 | 전용 `mail-triage`, 모든 도구 차단을 실행 전 검증 |
| 계정 | 개인 설정된 2개 | 1개 이상, `config.json`으로 설정 |
| 선별 | 세부 규칙 + AI | AI 중심, 불확실하면 승인함 |
| 자동 발송 | 사전 승인 견적 + 🔁 규칙 | **🔁를 누른 메일만.** 승인 문안 그대로, 규칙당 24시간 3통 |
| 자동 삭제 | 일부 규칙 | **없음.** 🚫 발신자도 휴지통이 아니라 스팸함으로 |
| Discord 결정 | 7개 반응 + 텍스트 수정 | 6개 반응 + 텍스트 수정 (🤝 제외) |
| 완료 스레드 | 검증 후 삭제 | 검증 후 보관·잠금 (교육 감사 흔적) |
| 전송 장애 | Telegram 별도 경고 | 원장·로그에서 직접 확인 |

### 🔁 자동 답장을 운영판보다 좁힌 이유

운영판은 한 사람이 지켜보지만 키트는 처음 설치하는 사람이 씁니다. 그래서 답장을 AI가 새로 쓰지 않고 **승인한 문안을 그대로** 보내 메일 속 지시가 답장에 섞일 수 없게 했습니다. 숫자가 하나라도 달라지거나, 첨부·계약·결제 표현이 새로 생기거나, AI가 확신하지 못하면 승인 카드로 돌아갑니다. 내 주소와 자동 발송 주소에서 온 메일에는 규칙을 만들 수 없어 자동 답장끼리의 반복을 막고, 그래도 생길 수 있는 반복은 하루 3통 한도에서 멈춥니다. 자동 답장 알림의 ⏸️를 누르면 규칙이 꺼집니다.

수업에서는 먼저 이 안전한 기본 흐름을 완성한 뒤, 자기 업무에 필요한 정책만 **명시적으로** 추가하세요. 자동견적이나 자동휴지통을 복사하는 것이 재현 목표가 아닙니다. 학습 목표는 **분리된 수집·판단·승인·실행·검증** 구조를 자기 계정으로 구현하는 것입니다.

## 수업 데모 순서

1. 개인 비공개 채널과 테스트 계정을 연결해 기준선 초기화.
2. 스스로 보낸 무해한 문의 1통이 요약·추천·스레드로 올라오는지 확인.
3. 다른 사용자의 ✅ 반응은 무시되고, 소유자의 반응 두 개는 충돌로 정지하는지 확인.
4. 본인 소유 테스트 수신자에만 ✅를 눌러 Sent 검증과 중복 방지 확인.
5. 동일 구조를 바꾸어 `VIP 보존`, `홍보 조용히 보존`, `사람 승인` 같은 업무 정책을 설계해 보기.

개인 메일·토큰·공개 서버를 수업용 데모 데이터로 사용하지 마세요. 공개 저장소에는 실계정 설정이나 상태 원장을 커밋하지 않습니다.
